The Jock Language — Description

Status: NORMATIVE. This document states what Jock is. It carries no chronology: when and why each rule became true is docs/record/language-arc.md, and every rule that has one links to it.

Rules carry flat L-n ids. The ids are append-only — assigned in the order they were written down, never in reading order, and never renumbered, because crates/, tests/ and tools/ cite them. Each rule names the corpus vectors that pin it, or says ⟨none — UNPINNED⟩ so the gap is countable rather than invisible.

The surface syntax is settled, and the release may ship zero-versioned precisely so it can settle further — so read the tables below as current rather than as a contract. The molds in crates/jockc/hoon/sur/jock.hoon ($keyword, $jpunc, $jatom, $tex, $jock-form) must match the tables here; a mismatch is a bug in one or the other.

Jock is a statically typed language that compiles to the Nock ISA (via Nockasm). Its syntax is Swift-inspired first, Rust-inspired second; its semantics are Nock-native (everything is a noun; functions are closures, emitted as cores at the ABI only — no core algebra is user-visible (types.md S9.8); recursion is the loop primitive). It is not an imitation of either source language: where Swift/Rust idiom conflicts with noun semantics, the noun wins.

Design principles

  1. One meaning per spelling. No syntactic form may mean different things in different contexts (see the adjacency law, §2.4).
  2. Kernel and sugar. Every construct is either a kernel form (one typed lowering rule, one Nockasm production) or sugar (one AST rewrite). A keyword enters the language only with: grammar entry, classification, its rule, and a positive + negative corpus vector.
  3. Loud failure. Where a plausible mis-spelling would otherwise silently change meaning, the grammar is arranged so it fails to parse, with a hint.
  4. Provenance. Every AST node, type expression, and emitted Nockasm node carries a source position.

1. Programs

A program is a sequence of ;-terminated statements followed by a final expression, whose value is the program's value:

let a: @ = 3;
func inc(n: @) -> @ { n + 1 };
inc(a)

L-184 · A program is ;-terminated statements followed by a final expression, whose value is the program's value. A missing terminator refuses %parse-expected %';', pointed at the start of the next statement. ⟨t-arc-term-semi, t-text-split-trail⟩

L-185 · Binding forms are STATEMENTS and require the ; — let, func, declarations, import, assert, assignment. Control expressions with braced bodies (if, match, loop) do not take a trailing ; when they are the final expression, and a braced declaration needs none at all (L-81). ⟨t-arc-decl-nosemi, t-arc-term-semi⟩

L-186 · Sequencing is EXPLICIT. Adjacent expressions never silently compose. Sequencing uses ;, and names enter scope through bindings, declarations and imports only. Juxtaposition does not exist anywhere in the grammar — collections and tuples are comma-separated (L-79) — so two adjacent expressions are either separated by ; or a parse error, which is what lets L-1 read whitespace as the only adjacency signal. ⟨t-arc-ctor, t-parse-unglued⟩

2. Lexical structure

2.1 Source, comments, identifiers

L-52 · Source is UTF-8 with LF-terminated lines. Tab and CR are lexical errors — loud failure, so there is no invisible-whitespace ambiguity to debug. ⟨t-lex-tab-n⟩

L-53 · Comments are // to end of line and /* … */, stripped by the lexer. Non-nesting. ⟨t-lex-comment-p⟩

L-54 · A comment separates tokens exactly as whitespace does. A token after a comment is never glued, so a comment can never create or destroy a postfix binding (L-1). ⟨t-lex-comment-p⟩

L-55 · Token positions are 1-based line and column, columns counting tape characters — bytes, for ASCII. Every lexer vector asserts the positions, so the whole vex-lex file pins this; the three named here are representative. ⟨t-lex-num-p, t-lex-type-p, t-lex-uni-p⟩

L-56 · There are two identifier classes, distinguished lexically. A name has a lower-case initial (foo, myCount) and denotes values, functions and fields. A type name has an upper-case initial (Point, List) and denotes types, structs, classes, traits and aliases. ⟨t-lex-term-p⟩

L-57 · The casing split is load-bearing, not convention: the parser distinguishes name tokens from type tokens, so it is the Rust convention enforced as grammar rather than as style. It is also what lets L-59 hold — a hyphen can be part of a name because no type name can contain one.

L-58 · An identifier is a letter followed by letters and digits. No underscores; _ is the wildcard. ⟨t-lex-term⟩

L-59 · Names admit glued hyphens, Hoon-Term-style. a-1 and foo-bar are each ONE name token, never a subtraction. A trailing hyphen (a-) is not a name and refuses. Hyphens never appear in type names — a - after a type name is minus. The readings cannot collide because binary - is spaced on both sides (§4.2). ⟨t-term-hyphen⟩

L-60 · Stdlib multi-word naming prefers hyphens; user style is free. Both hyphenated (starts-with) and camelCase (myCount, peekUnder) are legal everywhere names are legal. The prelude and stdlib prefer hyphenated Term-style for new multi-word names, with starts-with as the precedent, while existing camelCase prelude names stand. The rule governs what the stdlib adds, not what users write.

private — L-17 to L-25

L-17 · private marks the next declaration or func unexported. It registers, compiles and is fully usable inside its own module; it does not enter the module's $hlib. ⟨t-text-private-local, t-text-private-func⟩

L-18 · It is opt-out, not opt-in. There is no pub. A program that never writes the word cannot be broken by the feature existing — which is the whole reason the default is export.

L-19 · Visibility is module-scoped, following Rust: the declaring module and its descendants. 2.4 The adjacency law

L-1 · A postfix form binds only when glued

A call (, an index [, or a type application < attaches to the expression or type name before it iff no whitespace separates them. The lexer's glued flag is the whole mechanism; no rule anywhere consults anything else.

So fib(n) calls and fib (n) does not; xs[0] indexes and xs [0] does not; Map<@->@> applies and Map <@, @> does not; Point( x: 1 ) constructs.

⟨t-lex-glue-p, t-arc-ctor, t-lex-type-p⟩

L-2 · An un-glued postfix opener is an error, with a hint

Collections are comma-separated (§2.3), so nothing in the grammar is juxtaposition. An un-glued ( or [ after a complete expression is therefore never a second expression — it is a parse error naming the likely intent: %parse-unglued, hinting "f (x) does not call f; write f(x) to call, or ; to sequence".

In type position the same spacing is also an error but reports differently — List <@> refuses %parse-expected, because the type grammar fails before the adjacency check is reached. The outcome is identical; the tag is not.

⟨t-parse-unglued, t-lex-unglue-p⟩

L-3 · { is never postfix

A brace after an expression is always a block, in every syntactic context. There is no glued-brace form, so the braced constructor Point{ x: 1 } does not parse — it refuses %parse-expected. Construction is the glued paren, Point( x: 1 ).

⟨t-arc-ctor-brace⟩

L-4 · A block must produce a value, so {} refuses

Bare {} is not a collection literal and not a value; it refuses %parse-empty-brace. Empty collections are constructed or annotated — Set<@>(), or the empty map literal [->].

⟨t-parse-empty-brace⟩

L-5 · Why the law is kept

Not style. Two reasons, and both are load-bearing.

It is what makes L-2's diagnostic possible: a whitespace-blind grammar must guess what the user meant, and so cannot name the error. And it forecloses the JavaScript newline-swallow hazard, where a line break changes what the previous line meant.

It also removes an ambiguity Rust still carries. Because a brace after an expression is always a block (L-3), the Rust if a == Point { x: 1 } problem cannot be stated in Jock.

Record record/language-arc.md — OPEN-12, dissolved rather than resolved by the glued-paren move.

4.3 Casts and coalescing

p as (Float64, Float64)     // static cast:  must nest, checked at compile time

L-120 · as is STATIC. The source type must nest in the target and nothing is checked at runtime; a cast that does not nest refuses %mint-cast at elaboration. ⟨t-mint-cast, t-run-cast, t-err-chars-cast⟩

L-130 · Assignment is an EDIT, not a declaration. b = e edits an existing var binding through the kernel %edit (Nock 10); assigning a let-bound name refuses %mint-edit-immutable, and an unbound name is an error too. ⟨t-mint-edit-let, t-let-no-edit⟩

L-132 · var widening is SHALLOW. L-150 · Exhaustiveness is CHECKED; redundancy only partly, by a cover test over the scrutinee's type (types.md S12.3): a non-exhaustive match errors with a witness pattern, and an unreachable case is an error rather than a warning.

This said "by usefulness analysis", and types.md S12.3 had already corrected itself and said so: +mcov is a conservative five-case cover test, not Maranget specialize/default matrices. L-151 · switch is GONE, and the word is NOT reserved. Literal values are patterns (L-148), so match covers value dispatch with no second keyword.

This rule used to end "a retired spelling that becomes a legal variable name is worse than one that errors", and the word stayed in $keyword on that reasoning, refusing %parse-switch-gone with the rewrite named. Reversed 2026-10-29, deliberately and with the trade stated: a reservation taxes every program that would like the name, forever, while the did-you-mean serves only readers who remember a spelling that was never in a released Jock and has had zero call sites in this tree since before $patt landed. L-187 · mut is an ordinary name, as self is (L-158), and for the same reason. 9. What is deliberately absent

An absence is a rule like any other: something was asked for, ruled out, and now refuses or fails to parse. Each row says what the language does instead, and where the positive rule lives.

L-180 · The core algebra is not in the language. compose, object, and batteries and payloads are not user concepts. A core is a calling convention (types.md S9.8), reached by writing a closure or a trait, and a program never names one. L-181 · There are no trait objects or existentials. any Trait does not parse. L-182 · There are no exceptions, nulls, inheritance or macros. Failure is crash and the unit; optionality is T? (§3); reuse is traits and generics; and code generation is the compiler's business, not the program's. ⟨none — UNPINNED⟩

L-183 · The language has no self-hosting constructs. It cannot quote itself, stage its own evaluation, or reach its own AST.
